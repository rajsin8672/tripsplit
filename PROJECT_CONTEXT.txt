1. PROJECT OBJECTIVE & CANONICAL ARCHITECTURE
--------------------------------------------------------------------------------
TripSplit is a production-ready group travel expense-sharing web application with
accurate integer-paise mathematical splitting, Min-Cash-Flow debt minimization,
and peer-to-peer manual UPI settlements.

Strict Technology Constraints Maintained:
- Single canonical Express.js server on Node.js (v18+ LTS compatible).
- Express serves both static frontend assets (HTML, CSS, JS) and JSON REST APIs.
- Frontend uses modern Vanilla JavaScript (ES modules) and Vanilla CSS with custom properties.
- Zero frontend framework bloat (no React, Next.js, Vite, Angular, Vue, etc.).
- Authentication: Firebase Authentication (Email/Password) with browserLocalPersistence.
- Database: Firebase Cloud Firestore.
- Server Firebase SDK: Firebase Admin SDK verifying Bearer ID tokens on protected endpoints.
- Deployment: Render (One Web Service serving frontend and backend together).
- Payments: Manual UPI payments only (UPI deep links, client-generated QR code, UTR submission,
  receiver confirmation or rejection via Firestore transactions). No payment gateway or bank integration.

4. COMPLETE API ROUTE DOCUMENTATION
--------------------------------------------------------------------------------
All protected endpoints require Header: "Authorization: Bearer <Firebase_ID_Token>".

Public Endpoints:
- GET  /api/health
  Reports server health, uptime, timestamp, and Firebase Admin connection state.
- GET  /api/config/firebase
  Returns safe client Firebase Web configuration (apiKey, authDomain, projectId, etc.).

Authentication:
- POST /api/auth/sync
  Verifies ID token and creates or syncs Firestore profile in `users`.

User Profiles:
- GET  /api/users/me
  Returns profile of authenticated user.
- PATCH /api/users/me
  Updates allowed fields: `displayName`, `upiId`. Rejects attempts to alter immutable fields.

Trips:
- POST  /api/trips
  Body: { name, destination, startDate, endDate, currency, description }
  Creates trip, assigns creator as OWNER and ACTIVE member. Status: ACTIVE.
- GET   /api/trips
  Query: status (ACTIVE|ENDED), q (search text)
  Returns all trips associated with user, role, and active member count.
- GET   /api/trips/:tripId
  Returns detailed trip data. Rejects non-members with 403.
- PATCH /api/trips/:tripId
  Updates trip details. Allowed only if trip is ACTIVE and user is OWNER.
- POST  /api/trips/:tripId/end
  Transitions trip to ENDED. Disables further expenses, invitations, and financial edits.
- POST  /api/trips/:tripId/leave
  Leaves trip. Requires net balance to be 0 (factoring in confirmed settlements). Updates status to LEFT.

Members:
- GET  /api/trips/:tripId/members
  Lists all trip members joined with their display name, userCode, email, role, and upiId.

Invitations:
- POST /api/trips/:tripId/invitations
  Body: { email } OR { userCode }
  Invites a friend. Prevents duplicates and self-invites. Status: PENDING.
- GET  /api/invitations
  Lists all incoming invitations for authenticated user.
- GET  /api/trips/:tripId/invitations
  Lists sent invitations for a trip.
- POST /api/invitations/:invitationId/accept
  Validates recipient identity. Adds user as ACTIVE member, marks invitation ACCEPTED.
- POST /api/invitations/:invitationId/reject
  Validates recipient identity. Marks invitation REJECTED.
- POST /api/invitations/:invitationId/cancel
  Allows inviter or trip OWNER to cancel a PENDING invitation.

Expenses:
- POST   /api/trips/:tripId/expenses
  Body: { title, amount, category, paidBy, splitType, participantIds, customSplits, date, description }
  Calculates integer paise splits (EQUAL, EXACT, PERCENTAGE). Writes expense and splits atomically.
- GET    /api/trips/:tripId/expenses
  Returns expense ledger with splits, category icon, and member names.
- GET    /api/trips/:tripId/expenses/:expenseId
  Returns single expense with its splits.
- PATCH  /api/trips/:tripId/expenses/:expenseId
  Edits expense (creator or OWNER only; ACTIVE trips only). Recalculates splits.
- DELETE /api/trips/:tripId/expenses/:expenseId
  Deletes expense and splits atomically (creator or OWNER only; ACTIVE trips only).

Balances:
- GET /api/trips/:tripId/balances
  Computes Total Paid, Total Share, and Net Balance for each member.
  Verifies mathematical invariant: SUM(all net balances) === 0.

Settlements:
- POST /api/trips/:tripId/settlements/calculate
  Executes Min-Cash-Flow algorithm to generate minimized peer-to-peer settlement graph.
- GET  /api/trips/:tripId/settlements
  Returns existing settlements for trip with debtor and creditor profiles and UPI VPAs.

Payments:
- POST /api/settlements/:settlementId/payments
  Body: { upiTransactionRef, notes }
  "I Paid" submission by debtor. Validates UTR, checks duplicates. Status: REPORTED.
- GET  /api/payments
  Query: type (sent|received|all), status (REPORTED|CONFIRMED|REJECTED)
  Returns user's payment records.
- POST /api/payments/:paymentId/confirm
  Receiver confirmation. Validates payee identity; executes atomic transaction:
  payment -> CONFIRMED, settlement -> PAID. Prevents self-confirmation and double confirmation.
- POST /api/payments/:paymentId/reject
  Receiver rejection. Validates payee identity; updates payment -> REJECTED with reason.
  Settlement remains PENDING for resubmission.

5. MATHEMATICAL & FINANCIAL PRECISION RULES
--------------------------------------------------------------------------------
1. Integer Paise Standard:
   - Floating-point representations of currency are strictly forbidden in Firestore.
   - All monetary values are stored as integer paise (e.g. ₹5,000.00 = 500000 paise).
   - Conversions: `rupeesToPaise(val) = Math.round(val * 100)`.

2. Deterministic Remainder Distribution for Equal Splits:
   - When dividing total amount `T` (in paise) among `N` participants:
     `baseShare = Math.floor(T / N)`
     `remainder = T % N`
   - Participants are sorted deterministically by `userId` (alphabetical).
   - The first `remainder` participants receive `baseShare + 1` paisa.
   - The remaining participants receive `baseShare`.
   - Invariant: `SUM(allocatedAmount) === T` strictly.

3. Exact Splits:
   - User specifies exact share for each participant in paise.
   - Server validates `SUM(allocatedAmount) === totalAmount`. Rejects if sum mismatches.

4. Percentage Splits:
   - User specifies percentage for each participant.
   - Server validates `SUM(percentage) === 100.00`.
   - Each share: `Math.round((pct * totalAmount) / 100)`.
   - Any rounding discrepancy `diff = totalAmount - SUM(shares)` is deterministically absorbed
     by the participant with the highest percentage.
   - Invariant: `SUM(allocatedAmount) === totalAmount` strictly.

5. Net Balance Formula:
   - `Net Balance = Total Paid - Total Share`
   - Invariant: `SUM(all member net balances) === 0` strictly.

--------------------------------------------------------------------------------
6. SETTLEMENT ENGINE (MIN-CASH-FLOW ALGORITHM)
--------------------------------------------------------------------------------
- Purpose: Minimizes the number of peer-to-peer financial transactions needed to settle a group.
- Steps:
  1. Calculate net balance for each member.
  2. Verify balance reconciliation: `SUM(netBalances) === 0`.
  3. Separate members into Creditors (`netBalance > 0`) and Debtors (`netBalance < 0`).
  4. In a loop, select the maximum debtor (`abs(netBalance)`) and maximum creditor (`netBalance`).
  5. Settle amount `A = Math.min(debtor.owed, creditor.due)` in integer paise.
  6. Create settlement: `{ fromUser: debtor.uid, toUser: creditor.uid, amount: A, status: 'PENDING' }`.
  7. Update debtor and creditor remaining amounts. Remove fully settled entities.
  8. Repeat until all balances are zero.
- Guarantees:
  - Minimum number of cash transfers.
  - No self-payments (`fromUser !== toUser`).
  - No zero or negative transfers (`amount > 0`).
  - Total debtor payments strictly equal total creditor receipts.

7. MANUAL UPI PAYMENT SYSTEM LIFECYCLE
--------------------------------------------------------------------------------
1. Profile UPI Setup:
   - Users save their UPI ID (VPA) in Profile (validated by regex `/^[a-zA-Z0-9.\-_]{2,60}@[a-zA-Z0-9]{2,30}$/`).
   - Clear disclosure that syntax validation does not verify bank availability or ownership.

2. Settlement Payment Initiated:
   - Debtor views PENDING settlement owed to Creditor.
   - Debtor clicks "Pay via UPI".

3. UPI URI & QR Code Generation:
   - Generated URI format:
     `upi://pay?pa=creditor@vpa&pn=CreditorName&am=1666.67&cu=INR&tn=TripSplit%20Settlement&tr=SETTLE-ID`
   - Client generates standard QR Code Model 2 SVG without external network calls (CSP-compliant).
   - User can:
     - Scan QR Code with any UPI app (GPay, PhonePe, Paytm, BHIM, Cred, banking apps).
     - Tap "Open in UPI App" deep link.
     - Copy UPI ID and Amount.

4. "I Paid" Flow:
   - Debtor makes transfer in their external UPI app.
   - Debtor clicks "I Paid" in TripSplit and enters the 12-digit bank reference (UTR).
   - System records payment in `payments` collection with status: `REPORTED`.
   - Debtor cannot confirm their own payment.

5. Receiver Verification:
   - Creditor sees incoming payment claim in dashboard, trip settlements tab, and payments ledger.
   - Creditor checks their banking app or bank SMS to verify receipt of funds.
   - If credited: Creditor clicks "Confirm Payment".
     - Atomic Firestore transaction transitions payment to `CONFIRMED` and settlement to `PAID`.
   - If not credited or incorrect reference: Creditor clicks "Reject Payment".
     - Payment transitions to `REJECTED` with reason recorded.
     - Settlement remains `PENDING` so debtor can resubmit a corrected UTR.

8. SECURITY MODEL
--------------------------------------------------------------------------------
1. Server-Side Authorization:
   - All protected routes read `Authorization: Bearer <ID_Token>`.
   - Decoded via Firebase Admin SDK.
   - Zero trust in client-supplied `uid`, `role`, `status`, `amount`, or calculations.
   - Membership and role verification before reading or mutating trip data.
   - Ended trips are completely frozen against new expenses, invitations, and financial edits.
   - Debtors cannot confirm their own payments; only intended payees can confirm or reject.

2. Firestore Security Rules (`firestore.rules`):
   - Direct client writes to server-managed collections (`trips`, `trip_members`, `invitations`,
     `expenses`, `expense_splits`, `settlements`, `payments`) are completely denied.
   - Only backend Admin SDK can mutate financial ledgers.

3. Network & Headers:
   - Helmet with Content Security Policy allowing Firebase Auth CDN, Google APIs, and self-hosted SVG.
   - Rate limiting on API endpoints and stricter limit on authentication endpoints.
   - Sanitized input handling against XSS and injection.
